# Proposal: chore-parallel-changes

## Why

`AGENTS.md` правило 3 требует «one change fully closed before the next opens».
Правило нарушено на 6 открытых ченджах, и оно же неверно по существу: оно
запрещает нормальный рабочий режим (propose несколько, потом применять), не
защищая от реальной опасности.

Проверил пересечения по заявленным `Affected code`:

| файл | ченджи |
|---|---|
| `internal/mcp/tools.go` | `feat-mcp-paging-briefing`, `feat-mcp-trash-restore`, `feat-step-lifecycle-force` |
| `internal/cli/step.go` | `feat-step-lifecycle-force` |
| `internal/cli/doctor*.go` | `fix-env-doctor` |

Три параллельных изменения одного файла MCP — это не «нарушение порядка», это
реальный риск: три агента (или человек и агент) правят каталог тулов, каждый
видит только свою задачу, и результат merge может стереть чужую работу.

Как делают опытные (intent-driven.dev 2026-08-23; Nam Seob Seo 2026-05-24,
OpenSpec + OpenCode): propose на `main` → fan out в git worktree на каждый
ченж → каждый применяет изолированно → **verify против source-of-truth спеки**
перед merge → merge по порядку → archive. Параллельность разрешена и
автоматизируется, а конфликты ловит verify, а не запрет на само запрещение.

Правило 3 сейчас бесполезно и вредно: его нарушение не ловится (нет гейта),
а честное соблюдение (по одному) стоит реального времени.

## What Changes

Только `AGENTS.md` (и его зеркало в README, если там есть цитата правил). Кода нет.

- **Правило 3 переписано**: вместо «по одному» — «разные файлы или worktree».
  Формулировка: *propose нескольких ченжей разрешено; два открытых ченджа, которые
  правят один файл, не мерджатся без явного решения (второй переносится в worktree
  или ждёт) — конфликт фиксируется в proposal соседа.*
- **Правило 6 (close definition) сохранено** — оно про то, когда ченж закончен,
  а не про то, сколько их можно иметь открытыми.
- **Добавлено правило про verify**: перед merge проверить, что затронутые
  baseline-спеки не конфликтуют с дельтой соседа (соседний MODIFIED без
  выделения своей части = drift).

## Non-goals

- Не добавляю автоматический gate «два ченджа не правят один файл» в pre-commit:
  это false-positive-генератор (изменения в разных ченджах одного файла это
  нормально). Правило остаётся словом, но с явным критерием, а не с запретом.
- Не трогаю остальные правила (1, 2, 4, 5) — они работают.

## Impact

- Affected specs: нет (process/tooling change, как chore-remarks-pool).
- Affected code: `AGENTS.md`.
- Проверка: ни один гейт не меняется, поэтому регрессии в CI быть не может;
  DoD — файл валиден, все существующие правила на месте, новое правило
  сформулировано через проверяемый признак (пересечение файлов), а не запрет.

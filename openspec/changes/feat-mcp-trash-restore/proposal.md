# Proposal: feat-mcp-trash-restore

## Why

Агент через MCP может удалить проект (`delete_project`) и теряет путь
восстановления без захода в терминал: тулов `trash_list`/`trash_restore` нет.
Для памяти проектов, где удаление - самая опасная операция, это дыра.

Проверка premise по коду перед планированием:

- Транспорт уже есть: демон отдает `GET /api/trash`,
  `POST /api/trash/{name}/restore`, `DELETE /api/trash`; клиент и apistore их
  пробрасывают. Не хватает только двух MCP-хендлеров поверх готового.
- "Единый Restore, используемый CLI и MCP" уже единый: оба идут через
  `store.TrashRestore`. Делить нечего.
- "Restore молча берет первое совпадение" - такого кода нет. Текущий restore
  требует точное имя и падает на всем остальном. Нечеткий поиск проектируем
  с нуля, а не чиним.
- Бэкапов нет нигде. А `DeleteStep`/`DeleteBlocker`/`DeleteDecision` -
  жесткое удаление без корзины даже в CLI. Корзина покрывает только проекты.

## What Changes

Решения зафиксированы:

1. **Бэкапы на все удаления.** Перед каждым `DeleteProject`/`DeleteStep`/
   `DeleteBlocker`/`DeleteDecision` FileStore пишет бэкап в
   `_meta/backups/<unix>/`, ротация последних 20. Бэкап - страховочная копия
   для жестких удалений шагов/блокеров/решений, у которых корзины нет.
   Восстановление из бэкапа - вручную (файлы под git), процедуру описывает README.
2. **MCP: только корзина, не шредер.** Новые тулы `trash_list` и
   `trash_restore`. Тула `trash_clean` в MCP нет и не будет: агент не должен
   уметь стирать безвозвратно. `delete_project` без изменений (уже в корзину).
3. **CLI: полная мощность сохраняется.** `pm del` + `trash clean` стирают
   навсегда, как раньше. Новое - бэкапы делают жесткие удаления
   восстанавливаемыми вручную.
4. **Человекочитаемый листинг.** Имена в корзине сейчас `<uuid>-<timestamp>` -
   этим нельзя пользоваться. `TrashList` отдает структуры (имя в корзине,
   id, номер, title, время удаления), а не строки. Это меняет сигнатуру
   интерфейса, за ним едут CLI, API, apistore, mock и один тест.
5. **Restore по имени, номеру или title.** Точное имя - чинит. Номер или title -
   ищет среди удаленных; несколько совпадений - ошибка со списком кандидатов,
   ничего не восстанавливается. Неизвестное - ошибка с именем.
6. **Коллизия номеров при restore - отказ.** Восстанавливаемый проект хранит
   старый number; если живой проект уже занял номер - restore отказывает с
   понятной ошибкой, а не плодит дубли.

## Non-goals

- Корзины для шагов/блокеров/решений нет. Для них - только бэкапы. Полноценный
  step-trash - отдельная работа, не довесок.
- Бэкапы не версионируют каждое сохранение, только удаления.
- `pm doctor` бэкапы не чинит и не валидирует; только считает при желании
  человека посмотреть.

## Impact

- Affected specs: `mcp-server` (ADDED: 2 тула + запрет `trash_clean` в MCP),
  `cli-lifecycle` (MODIFIED: Trash - матрица поверхностей, было "CLI-only"),
  `project-store` (ADDED: бэкапы перед удалением).
- Affected code: `internal/mcp/tools.go` (2 хендлера + схемы + описания),
  `internal/store/store.go` (сигнатура `TrashList`), `internal/store/filestore.go`
  (бэкапы, листинг, resolve), `internal/store/mock.go`, `internal/api/server.go`
  (ответы под новый тип), `internal/client/client.go` + `internal/apistore/apistore.go`
  (проброс типа), `internal/cli/trash.go` (печать структур), `internal/cli/cli_test.go`
  (тест на новый тип), README.
- Соседи: baseline `cli-lifecycle` Trash говорит "Trash is CLI-only; no MCP
  tool exposes it" - станет ложью, правится MODIFIED в этом же чендже.
  Baseline `project-store` про бэкапы молчит - ADDED. P3 пула закрывается
  архивом этого ченжа.
- Пересечения по файлам: активных нет. `tools.go` после мержа blocker-refs
  свободен; `doctor*.go`/`flake.nix` не трогаем.

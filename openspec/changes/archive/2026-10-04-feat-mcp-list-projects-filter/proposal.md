# Proposal: feat-mcp-list-projects-filter

## Why

`list_projects` сегодня вызывается с `{}` и возвращает все подряд: active плюс completed. На живом сторе 9 проектов из них 3 completed, то есть треть ответа - шум, который растет линейно с каждым закрытым проектом. Главный расход не сам список, а fan-out: воркфлоу аудита делает `get_project` по каждому вернувшемуся номеру, и без серверного фильтра платит за закрытые дважды.

Сортировка это не лечит: порядок меняет, токены оставляет. Лечит только filtering (фильтрация) на сервере.

Прецедент в этом же репо: `feat-mcp-bounded-reads` перевел `get_project` на сводку по умолчанию с `detail:true` как escape hatch (запасной флаг), а `list_projects` прямо вынес в Non-goals как "отдельный вопрос". Этот ченж - тот самый отдельный вопрос.

Ограничение из правил сайзинга: дешевый ответ обязан COUNT (считать), а не прятать. Фильтр по умолчанию должен нести per-status счетчики, чтобы закрытые не исчезали молча.

## What Changes

- `list_projects` получает опциональный `status: active | completed | all`, default (по умолчанию) `active`.
- Default-ответ: в `projects[]` только active, плюс поля `active_count`, `completed_count`, `total`. Когда `completed_count > 0`, ответ несет hint (подсказку) про `status=all`.
- `status=all` возвращает прежнее поведение (все проекты), `status=completed` - только закрытые.
- Неизвестный `status` - ошибка с перечислением допустимых значений.
- Фильтр живет в MCP-хендлере (tool layer, слой инструментов). `Store.ListProjects` и HTTP API демона не меняются, как и требует правило "не перекраивать стор ради поверхности тулов".
- Описание тула обновляется: когда звать с каким статусом.

## Non-goals

- Не вводим пагинацию и курсоры: для десятков проектов фильра достаточно, прокручивать нечего.
- Не меняем поведение trash (мусорки): удаленные как не попадали в список, так и не попадают. Отдельный `trash_count` не обещаем в этом ченже.
- Не режем поля элементов списка (number/title/status/tags/goal/даты) - экономия тут от отсечения записей, а не полей.
- Не трогаем `get_project`, `list_steps`, `get_step` - их форма уже урезана в bounded-reads.

## Impact

- Affected specs: `mcp-server` (ADDED: требование фильтра списка).
- Affected code: `internal/mcp/tools.go` - регистрация `list_projects` (схема), `handleListProjects`, описание тула; тесты рядом.
- Пересечение файлов: активных ченжей нет (`openspec list` показывает только этот), `internal/mcp/tools.go` ни с кем не делится. Мердж без ожидания.
- Сосед по требованиям: `mcp-server` содержит `Tool catalogue` (derived, производный - числа не хардкодятся, правка не нужна) и сценарий `Call list_projects` под требованием `Tool input schemas` (вызов с `{}` по-прежнему возвращает список, теперь active по умолчанию - сценарий остается зеленым, его не трогаем).

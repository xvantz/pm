# Tasks: chore-briefing-spec (DoD обязателен)

Задача — зафиксировать работающее поведение брифинга. Не описывать код по памяти:
сверять с ним. Сверка нашла расхождение и потребовала правки кода — см. proposal,
раздел «Код оказался нужен — почему».

## Phase 1: Спека

- [x] 1.1 Capability `briefing`: purpose + требования по секциям, порядку,
  составу blocked, движению за день/неделю, долгоживущим блокерам,
  рекомендациям, фильтру по проекту, параметру `date`, degraded-чтениям
  **DoD:** `openspec validate chore-briefing-spec --type change` green
  **Результат:** 8 требований, 14 сценариев. Каждое утверждение сверено с кодом
  (`internal/briefing/briefing.go`), не с памятью: порядок секций — switch в
  Generate, взаимная исключительность active/blocked — тот же switch,
  `steps_today` vs `projects_moved` — счётчики в Generate, порог 7 дней —
  константа в цикле блокеров, плотные приоритеты — `prio++`.
- [x] 1.2 Не дублировать `project-store`: ссылки на `Event timestamps`,
  `Calendar-day bucketing`, `Unreadable timestamps are loud` вместо пересказа
  **DoD:** греп дельты на `RFC3339|2006-01-02|time.Local|UTC` не находит
  собственных формулировок про формат и зону — только ссылки
  **Результат:** правило зоны дня и формат меток упомянуты только ссылкой на
  `project-store`. Именно это и было причиной вынести спеку в отдельный
  чендж: одновременная правка обеих создала бы две правды об одном поведении.
- [x] 1.3 Отметить, что спека описывает наблюдаемое поведение, а не выбранную
  константу: порог «долгоживущего» зафиксирован как текущий
  **DoD:** в требовании `Long-lived blockers` порог назван, но не вынесен в
  отдельную настраиваемую величину
  **Результат:** порог 7 дней назван в тексте требования как часть
  наблюдаемого поведения, без `MUST` на конкретное число — чтобы смена порога
  была явным решением, а не молчаливым расхождением.

## Phase 2: Доказательства

- [x] 2.1 `spec_claims_test.go`: каждый сценарий спеки доказан тестом, а не
  заявлен
  **DoD:** для каждого из 8 требований есть тест; тест, написанный по спеке
  ДО правки кода, падает если спека расходится с кодом
  **Результат:** 7 новых тестов, все 8 требований покрыты:
  `ManyStepsMoveOneProjectOnce` (steps≠projects), `BlockedProjectIsNotAlsoActive`,
  `SectionOrderIsStable`, `FreshBlockerIsNotLongLived`,
  `RecommendationPrioritiesAreDense`, `SingleProjectFilterNarrowsEverything`,
  `UnparsableDayFallsBack`, `PausedIsCountedNotShown`.
  **Найденный баг:** `UnparsableDayFallsBack` упал — код откатывал вычисление
  на текущий день, но в ответе оставлял `date: "not-a-date"`. Ответ называл
  себя днём, который не считал. Исправлено в `briefing.go`: `date`
  приводится к фактически используемому дню, блок инициализации `b`
  перенесён выше парсинга.
- [x] 2.2 `validate --all --strict`, build, vet, тесты
  **DoD:** всё green; число тестов выросло
  **Результат:** **164 теста PASS** (было 156), `gofmt -l` пусто, `go vet ./...`
  чист, `validate --all --strict` 11 passed / 0 failed
- [x] 2.3 Коммит + PR, CI green, архив последним коммитом
  **DoD:** Forgejo run success; `openspec list` без `chore-briefing-spec`;

## Границы

- Правится ровно одна строка в `internal/briefing/briefing.go` плюс перенос
  инициализации; никаких других правок в `internal/` нет.
- Не задаём порог 7 дней как настраиваемую константу: спека фиксирует текущее
  поведение, изменение порога — отдельное решение.
- Не трогаем `feat-mcp-bounded-reads`: форма ответа тулов там.
